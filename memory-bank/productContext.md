# productContext.md — 為什麼要做工程審圖

> 只記錄「為什麼」與「痛點」，不記錄「怎麼做」（那是 systemPatterns.md / auditBasis.md 的事）。

## 痛點（待你補充/確認，目前是草稿假設）

1. **人力審圖速度跟不上圖說產出量**：工程圖說變更頻繁，人工逐張核對法規/標準耗時且容易漏看。
2. **審查依據分散在多份規範/標準文件裡**：審查者需要同時對照建築技術規則、結構規範、消防法規等，容易遺漏最新版本或誤用舊條文。
3. **審查結果與決策過程缺乏可追溯性**：人工審查往往只留下結論，沒有留下「依據哪一條、為什麼判定不合格」的軌跡，難以覆核與交接。
4. **跨人員/跨班次交接容易斷點**：審查進行到一半換手，後手不知道前手做到哪、卡在哪個問題 —— 這正是 `activeContext.md` 要解決的問題，用在 Agent 協作也是同樣道理。

## Hermes 想解決的核心問題

用雙 Agent 協同 + 有依據的審查規則（`auditBasis.md`）+ 不會遺忘的記憶（Memory Bank）+ watchdog 卡住偵測，讓審圖任務：

- 有明確、可追溯的判斷依據，不靠 Agent 臨場猜測。
- 卡住能被自動偵測，不會無聲消失在某個 Agent 手上。
- 換手/換 Agent 執行時，不需要重新摸索前面做過什麼。

> ⚠️ 待辦：以上痛點是根據系統目的推論的草稿，請你確認或修正為實際遇到的審圖痛點，這份文件才會是「真的痛點」而不是猜測。
